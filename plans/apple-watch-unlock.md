# Plan: Unlock the Omarchy lock screen with an Apple Watch

## Context

Goal: on the Dell XPS 14 (DA14260) running Omarchy 4.0.4, unlock the lock screen
while wearing an unlocked Apple Watch, the way macOS Auto Unlock does.

Apple's own Auto Unlock is macOS-only. The workable route is
[`watch-unlock-rs`](https://github.com/KatelynHaworth/watch-unlock-rs), a PAM module
that:

1. resolves the Watch's rotating Bluetooth LE address with its Identity Resolving
   Key (IRK);
2. requires the signal strength (RSSI) to be at or above a threshold (default
   −80 dBm);
3. reads the Watch's Apple Continuity "Nearby Info" advertisement and requires
   *Watch unlocked* and *Auto Unlock enabled*.

Other password-free options were ruled out on this machine. It has no fingerprint
reader: USB `06cb:0701` is the Synaptics SVP7500 camera bridge, not a sensor. The
HM1092 IR camera doesn't stream on Linux yet, so face unlock (for example Howdy)
can't work either.

## Findings so far

### Omarchy lock screen

The lock is a Quickshell plugin (`/usr/share/omarchy/shell/plugins/lock/Service.qml`).

- It **ignores `loginctl unlock-session`** and has no unlock IPC, so daemon-style
  tools such as `watch-unlock-linux` can't unlock it.
- It authenticates through two PAM services:
  - `omarchy-lock-password`: runs only after the user submits a non-empty input.
  - `omarchy-lock-fingerprint`: runs automatically and retries every 250 ms, but
    only if `fprintd-list "$USER"` reports an enrolled finger.
- Both PAM files are **generated by `/usr/bin/omarchy-apply-lock`** (package
  `omarchy`), which runs from `install/config/lockscreen-pam.sh` and
  `omarchy-upgrade-to-quattro`. Any local edit can be overwritten.

**Decision: hook into `omarchy-lock-password`, not the fingerprint slot.** The
fingerprint slot would re-run the Watch check in a loop and undo any manual lock
about a second after locking. It would also need a fake `fprintd-list`. The password
slot keeps an intent step, like a Mac: wake the screen, type any key, press Enter.

### Bugs found and fixed in `watch-unlock-rs`

Upstream `360aafc` found the Watch on the first run, then failed on back-to-back runs.

1. **Stale BlueZ cache:** BlueZ keeps a recently seen device for about 30 s after
   discovery stops, with its RSSI cleared. `discover_devices()` reports that cached
   entry immediately, the module saw "no RSSI" and gave up the attempt, and all
   three attempts hit the same stale entry within milliseconds.
2. **Discovery restarts:** the search was 3 × 500 ms, and each attempt stopped and
   restarted discovery. A resting Watch advertises less often, so 1.5 s of
   fragmented scanning missed it.

The fixes are on branch `fix/cached-watch-discovery`, in worktree
`~/repos/gh.katelynhaworth.watch-unlock-rs/.worktrees/fix-cached-watch`. Both
commits are signed and unpushed.

| Commit | Change |
| --- | --- |
| `d07048e` | `src/watch.rs`: use `discover_devices_with_changes()` and keep waiting until an advertisement supplies an RSSI |
| `ad11a91` | one continuous scan, bounded by a new PAM argument `search_timeout_ms` (default 1500) and a new `query_status --timeout-ms` flag |

Measured with `query_status --timeout-ms 10000`, Watch on the wrist next to the
laptop: **12 out of 12** runs found it, most in under 1.7 s, the slowest in 4.1 s,
at RSSI −60 to −66 dBm. Before the fix, 1 of 3 back-to-back runs succeeded.

Build artifacts: `~/repos/gh.katelynhaworth.watch-unlock-rs/target/release/`
(`libpam_apple_watch.so`, `watch_unlock_cli`). Build with
`CARGO_TARGET_DIR=<repo>/target make build` from the worktree.

### IRK

Copied from the Mac's iCloud Keychain: the `bluetooth` entry whose Account is
`Public: <Watch address>`, value under `Remote IRK`. It is stored base64-encoded,
exactly as Keychain shows it (the module reverses the bytes itself), in
`~/.config/watch-unlock/irk` (mode `600`). Treat it as a secret: anyone who has it
can track the Watch. Never commit it.

## Steps

**Status (2026-10-02):** steps 1–4 applied from `ad11a91`. In step 3, 4 of 5 runs
passed at the test service's default 1.5 s timeout. In step 5, `pam_test` against
`omarchy-lock-password` passed 6 of 6, each in 1.1 s or less, with no faillock
entries. The user confirmed the real lock-screen checks: Watch unlock with any key,
password fallback with the Watch locked, and a wrong password rejected. Sudo works
without a password prompt on this machine.

1. **Install the module:**
   `sudo install -m755 target/release/libpam_apple_watch.so /usr/lib/security/pam_apple_watch.so`
2. **Map the user to the Watch:** write `/etc/security/apple_watch.conf` containing
   `xdanger;<IRK>` with mode `644` and owner root. The lock screen runs PAM as the
   user, so the file must be readable by them; that's acceptable on a single-user
   laptop.
3. **Test the module in isolation:** install the repo's `conf/pam.d/apple-watch` to
   `/etc/pam.d/apple-watch`, then run `watch_unlock_cli pam_test xdanger` as the
   user. Expect `Authentication was successful!` with the Watch on and unlocked.
4. **Wire it into the lock** (only if step 3 passes): in
   `/etc/pam.d/omarchy-lock-password`, insert directly after the
   `pam_faillock.so preauth` line:
   ```
   auth       sufficient                  pam_apple_watch.so search_timeout_ms=3000
   ```
   - The later `[success=N]` jumps are relative, so inserting above them doesn't
     change their targets.
   - Faillock lockout still applies: a failed `required` preauth overrides a later
     `sufficient` success.
   - If the Watch isn't found within 3 s, the module returns `PAM_IGNORE` and the
     typed password goes on to `pam_unix`. With the Watch away, password unlock
     takes up to 3 s longer.
5. **Verify:**
   - Run `watch_unlock_cli pam_test xdanger omarchy-lock-password` with the Watch
     present. Don't test the Watch-absent case with the CLI: its `prompt_blind` is
     `todo!()` and panics.
   - Then the real check: lock (`Super+Ctrl+L`), type any key, press Enter. Repeat
     with the Watch locked or out of range: unlock must fall back to the password.

## Rollback

```bash
sudo omarchy-apply-lock                      # regenerates the stock lock PAM files
sudo rm /usr/lib/security/pam_apple_watch.so /etc/security/apple_watch.conf /etc/pam.d/apple-watch
```

## Risks

- **Weaker than Apple's Auto Unlock.** Apple uses distance bounding (time of flight)
  to resist relays. This checks only RSSI and the unencrypted Nearby Info flags.
  Someone who records the Watch's advertisement could replay it near the laptop
  until the address rotates (about 15 minutes). Treat it as a convenience, not a
  security boundary.
- **Lock-screen crash.** The module runs inside the Quickshell process. A panic
  would kill the lock client; Hyprland then stays locked on its crash screen.
  Recover from a TTY (`Ctrl+Alt+F3`), whose `login` PAM stack doesn't use this
  module. The only panicking paths need a successful find first, so this is
  unlikely.
- **Omarchy updates.** `omarchy-apply-lock` rewrites `omarchy-lock-password`, which
  silently drops the Watch line. That fails safe (password-only again) but needs
  re-applying.
- **Stale flags.** A cached device can briefly report the previous advertisement's
  RSSI and lock state, within BlueZ's ~30 s cache. It's acceptable when returning
  to the laptop, because the cache will normally have expired.
